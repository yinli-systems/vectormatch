# Cap4 V3 business batch: local functional candidate

This separate candidate starts from `9fda247d392432761a670de7c4d8040c7caff283`. It extends the explicit V3 endpoint only. The default V2 service/launcher and all previous branches remain unchanged. It is a local functional protocol candidate, with no cloud deployment, throughput improvement, W128 owner, sustained capacity, provider durability or 100M claim.

A new canonical `BusinessBatch` request contains one to four complete commands, bounded by the existing 4096-byte complete request envelope. Identities require positive account/sequence and an ASCII producer of at most48 characters. The same `(account, producer)` cannot occur twice in one batch, even with a different sequence. Complete decoding/canonical UTF-8 checks and response-space validation occur before item zero executes. A malformed tail cannot execute its valid prefix.

The new reply retains every index, full identity, canonical command SHA256 (`CommandCodec.request(0, command)`), complete Result/reason, replay flag, execution status and four-counter frontier. Actual codec limits, rather than the earlier design estimate, yield an attainable complete request maximum of **2639 bytes** and complete reply maximum of **4315 bytes**. The reply proof includes maximal scope, outer hash/error/counters, all tags/counts/lengths and four maximal entries. A valid 256-UTF16-unit reason has at most768 UTF-8 bytes (256 three-byte BMP characters), below the separate1024-byte encoder guard. The boundary test encodes four full Unicode results and all maximal outer fields, reaches4315 exactly, round-trips every reason, and remains below8192. No reason is truncated. The explicit formula and budget guard run before business mutation.

Execution is sequential prefix-commit. Each item obtains its own fresh admission at the current frontier; no token spans an earlier item. `APPLIED` means handed to core and includes a normal business rejection or cached replay, not necessarily an accepted order. A resource failure produces one `ADMISSION_REJECTED` entry without mutation, followed by `NOT_ATTEMPTED` entries with the unchanged frontier. Applied prefixes remain committed. No aggregate batch mutation is added. Business replays retain existing service application-mutation semantics while emitting no new business events and no maintenance-journal records.

The old V3 cache/snapshot contract allowed bounded UTF-16 reasons that need not be strict UTF-8. The batch endpoint performs a one-time, read-only scan of the bounded retained result cache before its first batch after start/restore. Unencodable retained text refuses that batch without mutation. This opt-in check does not change snapshot bytes, legacy single behavior or general core restore acceptance, and is not a per-business-command/full-journal scan. Fresh engine reasons are fixed ASCII. If an unexpected reply-value/encoding failure still occurs after execution, the adapter returns bounded `BATCH_RESULT_UNKNOWN`, never a successful batch or a rollback claim; the functional client preserves the complete original wire/identity payload for recovery. An explicit test injects incompatible cached text after the one-time gate and verifies this post-execution failure path.

The functional client remains one physical inflight operation. Its recovery exception and pending fence are in-memory only: they do not implement persistent client-restart recovery, cold-result lookup or global cache credit. The smoke explicitly writes diagnostic recovery files; that is not a production recovery store. An unknown batch fences different business input until the same complete batch is resolved. Its `UnknownBatchException` retains immutable logical commands and a clone of the original complete wire request/correlation; late correlations cannot satisfy a later exchange. A package-private functional fault seam can discard an application reply after validation; default public construction accepts replies normally. The real three-JVM smoke explicitly uses this seam once, observes UNKNOWN, verifies unrelated business input is fenced, and retries the original four identities. This is an application-layer reply-loss injection, not a UDP loss experiment.

This fence is **not** the future W128/global-retention-credit owner. Before capacity work, both batch1 and batch4 require a fresh common profile/owner with identical logical W128, task arrivalQ64 and separately recorded FIFO/session/MediaDriver/internal pending/flush/retention-credit dimensions. One unresolved producer must not be evicted by progress from other producers. The current smoke profile has16 producers,8 results/producer and64 global results; none of the current historical V2 capacity points is a valid baseline for this candidate.

Sync2, `force(true)`, archive implementation, NAK, idle strategies, maintenance ACK protocol and journal limits remain unchanged. Batching does not imply one force call per envelope. The finite maintenance journal still blocks indefinite endurance; no journal compaction, external durable exporter or cold-result lookup is added here.

Functional checks include canonical/maximal codecs, malformed-tail zero mutation, duplicate-producer refusal, exact per-entry reference results/frontiers, snapshots versus sequential V3 application, FIFO/events versus a separate single-command instance of the same MatchingEngine implementation (not an independent matching algorithm), partial history/outbox pressure, replay/conflict, strict cached-text admission, post-execution UNKNOWN and immutable recovery bytes. The fresh three-JVM smoke verifies actual reply discard/recovery, all-node matching checkpoint, exact owned cleanup, cold restart and continued batches with six first accepted orders. All attempts keep their native trees and raw wire/reference inputs. The archive helper reads back every native file SHA, length, mode and empty-directory inventory without extracting or deleting originals. Its gzip contains full logical sparse-file bytes; it does not claim physical sparse extent equivalence or permit unguarded restore.

Validation results, exact source hashes, commands and bounded evidence scope are recorded separately after the actual runs. Initial compile failures and every native smoke attempt are retained and are not counted as successful execution.
