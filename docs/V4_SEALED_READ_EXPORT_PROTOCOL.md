Current implementation:one bounded immutable read bank can be published by the service writer after PrepareArchive. It contains a defensive archive copy,complete contiguous captured outbox events,immutable reply counters,and a content/session-bound SHA-256 grant identifier. Only ArchiveChunk and FetchEvents can use a read permit;business,PrepareArchive,Position and ACK operations are rejected. A read holds exactly one version and returns historical counters from that version. It is not a live/linearizable state query,an authorization credential,or evidence of external durability. Counterparties must still verify complete canonical content and forced/readback file receipts before destructive acknowledgement.

At most one active read permit can retain a view. Publication/invalidation is confined to the service writer;read/close is confined to the permit owner. A read linearizes at acquisition and can finish from its immutable version after invalidation. No future acquisition can use an invalidated grant. The bank retains one current view,at most one reader-held old view,and at most one view being constructed;logical serialized input bounds are explicit. This is not an exact JVM RSS bound;the original prepared-archive cache and network response queue require separate accounting.

An explicit service constructor enables publication;legacy constructors retain no bank. onStart,role changes,termination,matching session closure,and effective archive/event cursor movement invalidate the bank. Rejected or idempotently replayed acknowledgements do not discard a newer bank if neither cursor changes. The bank is excluded from snapshots/state hashes;restart starts empty and requires a new logged PrepareArchive. Business may append after sealing;existing readers retain their original prefix and counters. Publication requires an exact current business cut. No default node launcher or network path selects this component yet.
