# Sealed historical export candidate

The previous first-segment experiment did not meet its registered10% native p99 criterion. In its C1 original wire tape,5001 FetchEvents and6189 ArchiveChunk requests enter the replicated log. Scheduled-to-dispatch p99 is52.782941ms,post-positive-offer p9912.310150ms,and globalp9959.093696ms. These separate percentiles cannot be added or subtracted. This motivates a new hypothesis,not an observed network-path gain.

Current implementation:one bounded immutable read bank can be published by the service writer after PrepareArchive. It contains a defensive archive copy,complete contiguous captured outbox events,immutable reply counters,and a content/session-bound SHA-256 grant identifier. Only ArchiveChunk and FetchEvents can use a read permit;business,PrepareArchive,Position and ACK operations are rejected. A read holds exactly one version and returns historical counters from that version. It is not a live/linearizable state query,an authorization credential,or evidence of external durability. Counterparties must still verify complete canonical content and forced/readback file receipts before destructive acknowledgement.

At most one active read permit can retain a view. Publication/invalidation is confined to the service writer;read/close is confined to the permit owner. A read linearizes at acquisition and can finish from its immutable version after invalidation. No future acquisition can use an invalidated grant. The bank retains one current view,at most one reader-held old view,and at most one view being constructed;logical serialized input bounds are explicit. This is not an exact JVM RSS bound;the original prepared-archive cache and network response queue require separate accounting.

An explicit service constructor enables publication;legacy constructors retain no bank. onStart,role changes,termination,matching session closure,and effective archive/event cursor movement invalidate the bank. Rejected or idempotently replayed acknowledgements do not discard a newer bank if neither cursor changes. The bank is excluded from snapshots/state hashes;restart starts empty and requires a new logged PrepareArchive. Business may append after sealing;existing readers retain their original prefix and counters. Publication requires an exact current business cut. No default node launcher or network path selects this component yet.

Next implementation:an explicit experimental export transport for sealed history,with bounded protocol frames,response correlation,session/scope/grant checks,actual route/image/MTU/message-size evidence,and complete original request/reply traces. Keep ordinary AeronCluster business,PrepareArchive and destructive acknowledgements at sync2. Distinguish direct read publication positions from replicated-log positions. Restrict the first native comparison to CLOSED read banks;do not imply that frozen counters are current when business is allowed between read banks. Lifecycle invalidation,backpressure,timeout/disconnect,wrong-scope/grant,partial or fragmented messages,slow consumers and cold restart need tests before native qualification.

The eventual native experiment must use one newly CI-qualified artifact for both the logged-read control and direct-read candidate,with identical enabled server footprint and only routing changed. Fix leader0,sync2,CONTINUE,CLOSED reads,agent100us,owner1ms,batch4/50us,cut1536,read32/page32/chunk6144,127 active producers and20-second arrivals. Register a500/s candidate qualification and two4000/s pairs before execution. Preserve every arrival,actual route,original frame,reply,forced/readback receipt,snapshot and cold restore. Existing all-arrival p99 rules and the10%/post-offer/no-goodput-regression paired criterion remain prospective;no result is claimed yet. The three JVMs share one CPU host.

The proposed internal export path is not yet an authenticated public trading endpoint. Production authentication,physical-host failure isolation,continuous100M,the<=5ms ten-minute production target and external venue/funded trading remain separate gates. No new cloud resource is required for this implementation work.
