# Retention V3 owner polling park experiment

This optional candidate changes the maximum requested park of the single `RetentionBatchOwnerV3` polling loop. It does not establish a throughput, latency, stability or endurance improvement. Both future arms must use the same candidate artifact and all other workload/configuration inputs.

`-Dvectormatch.retention.ownerPollMaxParkNs=1000000` selects the legacy1ms cap explicitly; `=100000` selects100us. Absence retains the legacy1ms path. Only those canonical decimal values are admitted. Hidden selection through `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS` or `_JAVA_OPTIONS` is rejected. This property is separate from `vectormatch.retention.idleMaxParkNs`, which configures the existing node/Aeron-driver policy; it is not propagated to child nodes.

The owner keeps its existing Config, batching flush deadline (50us by default, with the unchanged independent1ms validation ceiling), producer/retention credit, correlation, offer permits, retries, raw-wire identity, maintenance/read-bank windows and ACK exclusion rules. The only wait calculation change is the initial cap in the existing deadline-aware `parkDuration`. Earlier ready/permit/retry deadlines can still shorten that request. LockSupport or OS scheduling may wake late;100us/1ms is not an observed sleep duration or real-time guarantee.

Both previous constructors remain and use the legacy1ms cap. An explicit public constructor accepts the validated cap, and a package constructor also accepts the existing fake clock. Validation happens before factory invocation or owner-thread construction. The polling property is selected by the capacity harness rather than implicitly changing every legacy owner instance.

Owner snapshots always record `ownerPollMaxParkNs`, `ownerPollRequestedSleepOnly=true`, `ownerPollOsLatenessBounded=false` and the corresponding truthful waitPolicy. When the property is explicit, configuration.json and load-result/failure.json additionally contain `ownerPollSelection` (intent) and `ownerPollActual` (values read from the constructed owner's snapshot). Intent/actual cap mismatch is rejected; a missing owner is explicitly unavailable. Pilot registration records selection intent before owner construction and must be reconciled with those actual load/snapshot records. Legacy absence adds no new selection fields to configuration/summary/registration.

The pilot validates selection at all public entry points before creating a directory or checking/choosing ports. Experiment construction validates before its first filesystem write or factory work. Invalid values do not create a partial trial.

Source-only preparation includes eight new deterministic test methods covering canonical/hidden/namespace policy, constructor pre-factory failure, early pilot/experiment rejection, both old constructor defaults, unchanged flush ceiling, actual-versus-intent metadata, same original identity/wire and UNKNOWN credit through late completion, and read-bank retained credits/fences with reverse and duplicate replies. They reuse the existing FakeIO/service fixtures through two additional test-only constructor overloads. No test asserts exact wall-clock sleep or throughput. Root must review and execute tests and native validation; they have not been run by this implementation task.

A prospective comparison keeps source/artifacts/profile, selected readWindow8,6144-byte archive chunks, fetch16, businesscap4, W128/Q64, setup, rate/duration, sync2/force, appointed leader, MTU, node/driver policy and all resource/retry limits fixed. Only explicit owner poll cap1ms/100us differs; the new artifact's common plans and actual owner metadata must be verified in both arms. A1/B1/A2/B2 preserves every outcome, CPU cost and scheduler quality. The historical6033 CPU point is separate;100M journal retention remains unresolved by this change.
