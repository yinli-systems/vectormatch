# Finite V3 open-loop source

This candidate measures continuously scheduled business arrivals while the same client performs bounded external archive/event maintenance. It is a functional prototype, not a capacity, endurance, multi-host, or 100M proof. Default V2 and the previous synchronous functional client remain unchanged.

Both prospective arms use the same finite V3 profile/artifact, logical workers128, external FIFO64 per worker (8192 positions), one unresolved command per producer, internal pending128, one physical session/shared driver, fixed leader0, and unchanged durable sync2. The sole arm variable is business frame cap1 or4, with a50us flush deadline. Owner wait remains at most1ms, subject to OS scheduling.

An independent monotonic arrival scheduler releases every planned arrival at its fixed offset. Maintenance drains dispatch, never pauses this clock. Queues can fill/reject while dispatch is stopped; all such arrivals retain their original index/identity. Worker=index%128 and request sequence=1+index/128, so unsent arrivals leave legal high-water gaps. No UNKNOWN is assigned a fresh key. Each physical retry preserves the original frame correlation and bytes. A2-second per-dispatch offer permit admits at most4 positive offers; a global positive retry cap and finite negative cap abort the source if exhausted. Offer return observation is not business acceptance.

Per-arrival primitive columns retain scheduled/arrival/dispatch/submit/first offer-call/first nonnegative offer-return/reply-completion/first UNKNOWN observations, original business hash, correlation and batch index, result/admission/replay status. `firstPhysicalAdmissionNs` means the monotonic observation after a nonnegative publication.offer return, not an exact internal Aeron publication timestamp. All timestamps are local monotonic; UTC origin is an approximate mapping. Missing observations remain empty/null, not zero. Full wire requests/replies and every offer return code are retained in bounded streamed tapes; no complete350k command/ticket/wire object graph is retained.

All-arrival ACCEPTED p99 is defined only if every planned arrival confirms one distinct ACCEPTED order, with no loss, unresolved command, rejection, duplicate or unreleased item. A separate all-arrival REPLY p99 includes finite business-rejection replies. Conditional reply/accepted quantiles use nearest rank and retain their denominators. An original arrival first confirmed by replayed reply may count once as accepted; repeated order IDs never count twice. Physical admission counts, logical business replies, unique accepted orders, setup and maintenance are separate.

Every3072 completed business commands, dispatch drains and exports the exact canonical/hash-linked history and events, forces and reads back the external payload, then issues same-identity ACKs. The first cut includes3 setup commands; the prospective plan conservatively budgets an additional separate setup cycle, so its115-cycle/920-record350k bound is an upper bound, not an observed count. Timing CSV records every maintenance RPC and cycle. Maintenance time remains inside the source window/drain. No directory-fsync or independent durability claim is made.

Prospective admission derives finite exact codec witnesses (including long sequence digits, producer identity bytes, requests, complete replies, archive/event payloads, both logical/physical tape copies, attempt/index/arrival/timing CSV and metadata). The declared workload requires successful BUY1 IOC execution with two events per order; external physical-order reference and final snapshots verify this assumption after a functional run. Arbitrary malformed replies, excessive retries, unexpected output or native allocation growth abort rather than imply a business capacity failure.350k execution requires explicit admission of all trace, payload, journal, writer file/byte and native-growth bounds, plus fresh full-owned-root usable-space checks. Sampling `st_blocks*512` and a free-space floor is a stop guard, not an atomic quota or proof against arbitrary native growth.

A1Hz observer walks only the owned state root and records non-atomic queue/pending/phase/free/allocated snapshots and its own elapsed time. A bounded owner-thread observation records actual leader/term and accumulated leader events initially, each second, and before close; fixed-leader/term deviations fail the source. No position/hash RPC is added inside the business window. Full source overhead and setup exclusion are explicit; future capacity runs must retain every registered outcome and use separate correctness/configuration/timing gates.

The local functional pilot is6400 arrivals at500/s (12.8seconds), two fresh cap1/cap4 three-JVM clusters on one host, crossing multiple maintenance cuts. It replays actual physical requests into a sequential reference, verifies final full counters/hash and all three snapshot logs, and preserves all attempts and original native bytes. This does not prove stable throughput or persistent client crash recovery. The finite maintenance journal still prevents a100M lifetime claim.
