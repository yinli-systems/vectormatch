# Sparse versus zero-materialized segment-shaped files

Prospective standalone filesystem experiment only. Four sequential arms C1,D1,C2,D2;control uses RandomAccessFile.setLength(128MiB),candidate fully writes128MiB of zeroes before the timed workload. Three Java writer threads/files per arm,3,000 consecutive4KiB writes per thread,each followed by FileChannel.force(true). Same actual pinned Linux JDK,filesystem,heap and executable. No JFR or live cluster;no sync-level reduction. All arms use identical deterministic payloads and fresh owned paths. Original app state and archive files are never opened.

Before timing:force(true) each initialized file and directory,prove process identity and ready paths,record stat size/allocated blocks for all three files. Candidate must be fully allocated;sparse control must not be fully allocated. Per-thread write and force monotonic start/durations are all retained;verify every byte of all128MiB files against independently reconstructed deterministic payload plus zero tail and record full SHA-256. Retain all files,failures,setup duration and per-thread distributions. Global start/end and per-thread start skew remain explicit;this is closed-loop storage timing,not order throughput.

Candidate screening:in both adjacent pairs,every writer must have force p99 at least10% lower and no worse per-thread full-work duration. This is screening only;no native improvement or default promotion follows. Failure to allocate or preserve evidence invalidates the arm. No workload overlap;maximum1.5GiB retained data+bounded logs;free space must remain>=3GiB before each arm and>=1GiB throughout. No new cloud resources.
