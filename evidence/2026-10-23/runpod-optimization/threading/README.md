# Controlled node MediaDriver threading comparison

**The threading comparison is complete: all four 15k windows are valid but nonstable, and DEDICATED performs worse than its paired SHARED control on these resources.** DEDICATED accepted-window goodput is 8.992% and 5.172% lower in the two pairs; returned-command scheduled p99 is 34.765% and 8.387% higher, with more client admission loss. Every formal window has missing offered arrivals, so all-offered accepted p99 remains null. No negative round is removed and no higher stable arrival rate is claimed.

This registered A/B/A/B comparison changes node MediaDriver scheduling from `SHARED` to `DEDICATED`; the client MediaDriver stays shared in both groups. DEDICATED adds the expected server runners and consumes more node CPU, with larger observed throttled-time increments, but those observations do not uniquely explain the performance difference. Prior buffer/client-driver results remain separate configurations, not replacement controls.

## Why the buffer returns to its control value

The preceding [network comparison](../network/README.md) retains all four nonstable windows and actual socket-buffer attestations. Increasing receive memory eliminated the selected follower LOG socket's measured drops in those observations, but did not establish a higher stable rate or lower returned-command p99. The unchanged controls also varied. This threading comparison therefore fixes the receive request at 131,072 bytes and tests scheduling independently; it does not discard the larger-buffer result or assume the two factors cannot interact.

Each threading run retains before/after owned-socket probe results. Requested values and actual Linux `rb`/`tb` kernel-memory limits must be kept distinct; the latter often double requested values. Probe PID/start-time/inode checks, actual values and any diagnostics must pass before claiming the intended buffer control. Broad pre/post drop counters include setup/validation; strict interior matching-socket attribution is used for load-window deltas. Zero sampled socket drops cannot establish an entirely loss-free network.

## Reconciliation and interpretation

Independent streaming of all four CSV files accounts for 760,000 scheduled arrivals, 733,025 accepted executions and 26,975 explicit client-FIFO not-sent arrivals. Accepted results split into 700,926 confirmations within arrival windows and 32,099 during drain. Every per-run goodput and nearest-rank scheduled p99 reproduces its result artifact within floating-point rounding. Source/configuration/leader checks and canonical snapshot/asset/order/event checks pass, while all four windows fail the registered stability rule. Per-reply replay uses the same `MatchingEngine` in actual command-sequence order, not an independent matching algorithm.

Both DEDICATED windows have lower observed goodput, higher returned-command scheduled p99 and more admission loss than their paired SHARED controls, while consuming more server CPU. This is a repeated negative result for this finite-window deployment; it does not justify weakening the validation rule or selecting a different round. More aggregate runners do not establish a faster path. Throttle bursts, compilation, transport recovery, runner coordination and shared-host scheduling observations do not uniquely isolate all of the difference, and these fresh-process windows with 100 warmup commands do not establish an indefinitely warmed steady state.

The evidence supports keeping node `SHARED`, the 131,072-byte receive request and the resource-saving shared client driver as the explicit control for a separately registered concurrency-window test. A future 128/256-client comparison or larger fixture must retain its own node/load/profile/session limits and preparation identity, with matching new controls; it cannot be pooled into this threading result. No matching rule, durability setting, business identity, unknown handling or stability criterion is relaxed to claim improvement.

The total project budget remains USD 20 with no new resources. Budget receipts are launch-time/rate estimates, not reconciled billing. The separate 100-million cumulative-unique-command, commands-per-second and simultaneous-connection goals remain unverified; independent fresh trials with deliberately repeated identities cannot be pooled into a globally unique 100-million-command run.
