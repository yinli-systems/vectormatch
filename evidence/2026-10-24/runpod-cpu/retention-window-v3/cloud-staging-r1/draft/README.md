# Root-controlled window staging and launch draft

These adapters target only the existing CPU host and canonical `/opt/vectormatch-cpu/preparation/window-cloud-abab-r1`. This preparation has executed only 23 local pure Python guards. Neither adapter, SSH, Java, native workload, resource creation, signal or original-state mutation was executed by this task.

`stage_window_cloud.py` accepts the immutable root evidence freeze and its explicit SHA. It accepts only root-created ready release bytes; it never flips the immutable candidate's readiness. Runtime/configuration/plans/JDK/classpaths/artifacts must remain identical to that candidate. The actual source/native/133-test proof, stopped Linux metadata JVM, Java source identity, JDK bytes and actual plans are hash bound. No new original/PG baseline is generated.

Root staging invocation uses `python3 -B stage_window_cloud.py --root-freeze <absolute ROOT_FREEZE.json> --root-freeze-sha256 <root-verified SHA> --output <fresh local directory>`. Both imports and remote commands disable bytecode writes. Exact host/Linux/x86_64/root/JDK/free-space checks precede source upload. Upload and extraction are exclusive, allow only 23 frozen files and at most 32MiB, and reject traversal, links, duplicates, unexpected members or changed SHA/mode/size. Full TAR validation completes before creating the fresh canonical preparation. Source files are rehashed after extraction. Partial uploads/preparations remain as failure evidence; there is no retry, deletion or cleanup of unrelated workloads.

Staging runs exactly the four frozen Python unittest modules and requires the actual Linux output to show all 122 guards passed. It then invokes the frozen controller with `--round 1 --release-sha256 ...` and no `--start-new`. Owned read-only Python subprocess timeouts are bounded internally; failures/partial output remain in the fresh staging output. Only success writes `STAGE_SUCCESS.json`, with full source rows, exact bundle/release/root-freeze SHA, guard count and default preflight receipt. No benchmark starts during this step.

`launch_window_cloud.py` is separate. Root must independently review `STAGE_SUCCESS.json`, supply its exact SHA via `--stage-success-sha256`, and name a fresh output directory. It revalidates all local frozen rows and all remote source bytes before one explicit `--start-new`. The exclusive remote `round-N-execution-register.json` is append-only JSONL, preserving intent, early spawned PID, and stable start-tick/full argv observations; its name plus stdout/stderr remain the same three metadata files expected by the collector. The collector and native auditor treat these outer metadata files as opaque bytes. Launch stdout remains one final JSON object. Any missing/changed identity or SSH timeout means inspect the existing attempt read-only; never submit another launch.

Round2 additionally requires `--prior-collection <root-frozen independent round1 gate>` and its SHA. Root must first exclusively upload those exact gate bytes to `release/round-1-collection-gate.json`. The launcher never infers collection from exit0 or auto-uploads/promotes a gate. The frozen controller independently checks actual round1 closure, compressed archive, complete member inventory/readback and retained native trees before starting round2. No automatic second round is performed.

`ROOT_FREEZE.template.json` is an internal root evidence-attestation template, not a user permission flow. The real candidate remains false/immutable. `test_stage_launch.py` uses actual frozen metadata for its positive source/JDK/plan bindings and local contract fixtures for failure rejection. Guard attempt registrations, stdout/stderr, completion and exact source copies are preserved separately. No fabricated plan witness or cloud success is claimed.
