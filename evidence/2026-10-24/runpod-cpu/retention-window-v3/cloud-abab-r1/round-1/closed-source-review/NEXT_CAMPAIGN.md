# Next campaign: bounded latency factor, then ten full cuts

This is local preparation, not an executed benchmark, exact JAR admission, or a capacity claim. Current 6,400 arrivals at 500/s span 12.8 seconds and only two complete 3,072-command cuts, followed by a partial cut. Two full-cut boundary observations cannot establish sustained capacity or unbounded queue drift. Released but not fully confirmed work is an end-to-end backlog, not the owner queue.

## Minimum useful longer baseline

A fresh 30,720-order campaign at 500 arrivals/s spans 61.44 seconds and crosses ten full cut boundaries (setup contributes three commands). Keep business batch 4, read window 8, archive chunk 6,144, event fetch 16, W128/Q64, leader 0 / term 0, force and sync 2, MTU 1,248, all retry and journal caps, and the same fixed profile. Evaluate backlog immediately before each full cut and after recovery, accepted throughput, p99, unknown, rejection and not-sent counts over all ten cycles. Exclude the final partial cut from the full-cycle drift comparison and report final drain separately.

Existing Config admits 10–120 second source windows, arrivals <=350,000. Consequently 61,440 orders at 500/s is invalid (122.88s); 60,000 at 500/s is 120s but a sequential pair exceeds the existing controller's 240-second execution budget before startup/drain. Do not widen that deadline in the current artifact. 30,720 at 1,000/s is 30.72s; at 2,000/s it is 15.36s; at 3,000/s it is 10.24s. Rates above 3,072/s need more arrivals for the existing ten-second minimum, and must receive their own actual-JAR plan admission.

For 30,720 arrivals, the conservative prospective cycle count is 1+ceil(30720/3072)=11, hence 88 bounded journal records under the existing planner formula (11*2*4), not a reason to enlarge the 4,096-record / 4MiB service journal. The admitted 6,400-arrival Linux plan has raw=38,033,404 bytes and allocated=589,327,865 bytes including the shared 536,870,912-byte native reserve. Five complete small-run envelopes cover 32,000 arrivals and 20 prospective cycles: a planning-only upper estimate is raw <=190,167,020 and nativeReserve+5*(smallAllocated-nativeReserve)=799,155,677 bytes. This is an envelope arithmetic check, not the exact future planner result. The future exact distribution must independently plan 30,720 arrivals and pass the unchanged hard 2GiB raw / 2.5GiB allocated-growth caps before release. The prospective 350k common full-hash plan already fails 2.5GiB; do not widen this cap.

The smallest future load change is parameterizing the pilot/harness arrivals and rate, with its existing 6400/500 defaults unchanged, and selecting a single fixed window-8 arm. The engine, owner, protocol and state profile already support the bounded workload; no protocol or resource-cap change is justified. Do not combine this workload change with the idle-factor comparison.

## Next single factor

First close the current read-window A/B/A/B raw evidence. Then use one NEW artifact for both explicit idle arms: maximum requested park 1,000,000 ns versus 100,000 ns. Keep each role's actual spin/yield/minimum park and all other factors unchanged. Use fixed read window 8 in both arms. A 100us requested park is an OS request, not a real-time latency guarantee. Compare CPU cost, scheduler delay, maintenance duration and end-to-end p99, not just RPC medians. Do not add dedicated threads, busy spin, CPU affinity, governor, timer-slack or force-level changes in the same experiment.

Record per-owned-process CPU seconds and, where practical, per-owned-thread CPU / voluntary and involuntary context switches over idle, arrival and maintenance intervals. Report consumed cores (CPU seconds / wall seconds), CPU per accepted order, process RSS and disk growth, plus throughput/p99 and backlog at equal cut positions. The host's 32 logical threads / 16 physical cores are shared hardware, not an exclusive-core guarantee. A later ten-full-cut campaign establishes whether an apparent latency improvement also preserves cycle-to-cycle recovery; the short fixed-6400 campaign only compares that bounded workload.

## Pinned effective idle defaults

The node and owner MediaDriver currently explicitly install Agrona's no-argument BackoffIdleStrategy, so their effective tuple is 10 spins, 5 yields, 1,000ns minimum park, 1,000,000ns maximum park. In contrast, Aeron's default factory constructs 10 spins, 20 yields, 1,000ns minimum park, 1,000,000ns maximum park for Archive, consensus and clustered service. Each role needs a distinct mutable strategy instance. Default behavior and property resolution remain unchanged when the new opt-in is absent.

Primary pinned sources: [Agrona 2.6.1 BackoffIdleStrategy](https://raw.githubusercontent.com/real-logic/agrona/2.6.1/agrona/src/main/java/org/agrona/concurrent/BackoffIdleStrategy.java), [Aeron 1.53.3 driver Configuration](https://raw.githubusercontent.com/aeron-io/aeron/1.53.3/aeron-driver/src/main/java/io/aeron/driver/Configuration.java), [Archive](https://raw.githubusercontent.com/aeron-io/aeron/1.53.3/aeron-archive/src/main/java/io/aeron/archive/Archive.java), [ConsensusModule](https://raw.githubusercontent.com/aeron-io/aeron/1.53.3/aeron-cluster/src/main/java/io/aeron/cluster/ConsensusModule.java), [ClusteredServiceContainer](https://raw.githubusercontent.com/aeron-io/aeron/1.53.3/aeron-cluster/src/main/java/io/aeron/cluster/service/ClusteredServiceContainer.java).

Archive's `aeron.archive.idle.strategy` and cluster's `aeron.cluster.idle.strategy` select the factory; `aeron.shared.idle.strategy` is bypassed by the current explicit MediaDriver instance. The recognized backoff alias does not expose a numeric max-park JVM property. Reflection custom classes use no-arg constructors. A new explicit opt-in must reject conflicting/ambiguous idle overrides rather than silently change their semantics.

ZIP-only inspection of the current frozen release confirms that Aeron-all and standalone Agrona contain identical BackoffIdleStrategy.class (3,401 bytes, SHA256 0452091ff408a7407b1831b9ad5976310ebd93e8b88fe9b5fbc158d95cc5d38b) and BackoffIdleStrategyData.class (830 bytes, SHA256 95591090ee89fd4c1e0939ee8f0b156a13c91cb80949cef0b04009d47138d021). No JVM or network benchmark was run to establish these byte identities.
